### 부분 발송 큐 충돌 복구 (2026-10-15, Codex)

사용자가 전체 재점검·수정·정상화를 승인했다. 기준 main `78e9a6a4`, 작업 브랜치
`codex/risk-delivery-recovery-20261015`. 실제 운영 회차 `risk-production-38684445708`은
Actions `38689361007`에서 수신자 3곳 중 2곳 accepted 후, 마지막 대상의 **SMTP 전
큐 선기록 PUT HTTP 409**로 중단됐다. Gmail의 운영 발신본 2건은 비공개 preview와
HTML 바이트가 일치한다. 마지막 대상은 영수증·시도 횟수가 없어 미시도로 확인된다.
409 응답 본문은 이전 코드에서 폐기해 정확한 서버 측 충돌 유형은 소급 확정할 수 없다.

- 큐 409는 타입과 안전한 request ID/종류만 보존한다. 원문 응답·키·주소는 공개 로그에
  출력하지 않는다. 영수증은 이동하는 main 대신 커밋에 고정해 읽는다. 동일 파일 SHA가
  유지된 명시적 충돌만 최대 3회 동일 CAS로 재시도하며, 파일/영수증이 바뀌면 중단한다.
  고유 delivery_revision으로 같은 쓰기의 반영 여부를 구별한다. 네트워크·5xx 등 결과가
  불확실한 쓰기와 SMTP DATA는 자동 재시도하지 않는다.
- 원자적 review/job ACK도 타 봇의 무관한 브랜치 커밋 충돌 때만 원본 SHA를 다시
  확인해 최대 3회 새 base tree로 재구성한다. 원본 변경·불명확한 실패는 중단한다.
- native 파이프라인은 임시 seen 파일에 예정 이력을 계산한다. 메일·제목·수신자 해시·
  분석/정책/입력 해시·예정 이력을 비공개 `outbox/<job_id>.json`에 먼저 고정하고 읽어
  확인한 뒤 SMTP를 호출한다. 운영 seen은 전원 accepted 뒤에만 반영한다. 본인 검수는
  운영 이력 쓰기 0을 유지한다. 고정본·분석 결과는 덮어쓰지 않는다.
- 명시적 `recover`는 기존 수신자·고정본·정책·입력·본문·main 이력을 재검증한다.
  accepted만 건너뛰고 **영수증도 시도도 없는 대상만** 같은 메일로 처리한다. sending/
  uncertain/rejected 수신자나 시도 횟수 불일치, 내용/수신자/이력 변경은 차단한다.
  일부 발송 회차의 복구는 최초 생성 후 24시간 이내로 제한하며, 미발송 회차의 TTL을
  연장하지 않는다. 전원 accepted인 이력/ACK 복구는 SMTP 0이다. 완료 요청은 noop이고
  워크플로가 ACK를 재실행하지 않는다. 정상 분석 예약의 uncertain 차단은 유지한다.
- 고정본 도입 전 실패 회차만 `recoveries/<job_id>.json`의 운영자 검증 자료와 Gmail

  기존과 같이 전원 접수·main 이력 저장 후 ACK와 원자적으로 확정한다.
- 검증: `run_tests.sh` 13개 스위트, 원본 미탐 0/39, `check_changes.py` 통과.

## 5. 미결 — 브랜치 `perf/filter-omit-negatives`

**main에 병합하지 않았다.** 검수 대상이다.

### 변경 내용

1. 1차 필터에서 **relevant:false 기사를 배열에서 완전 생략.** 최초 실험은 기존
   파서를 유지했으나, 후속 수정에서 엄격한 JSON·ID·완료표시 검증을 추가했다.
2. 배열 마지막에 `{"id":0,"seen":N}` sentinel 요구. 생략하면 '응답 잘림'과
   '전부 false'가 구분되지 않기 때문. id 0은 기사 id(1-base)와 겹치지 않아 무해.
3. 최초 구현은 재실행 후 건수 많은 쪽만 채택했으나 누락·None 오류를 발견. 후속 수정은 전건 명시 방식 재판정, 기사 ID 합집합, 최고 등급 보존. 재판정도 불완전하면 명시적 실패.
4. 배치별 `expected/reported/returned`를 `filter_seen_detail`에 기록.

### 실측 결과

| 회차 | 수집 | 선별 | 기사당 출력 | seen 불일치 |
|---|---:|---:|---:|---:|
| 09-26 20:08 | 198 | 0 | **0.69 tok** | **1** |
| 09-26 20:13 | 197 | 0 | **0.32 tok** | 0 |

실험 비교 12.97 → 0.69 tok/건 (**−94.7%**). **월 절감 약 $3.8은 기존 추정**이며,
positive 검출과 재시도 비용을 실제 API에서 검증하기 전 확정 절감액으로 보지 않는다.

### 병합을 보류한 이유

- **`selected 0`이 4회 연속.** false 생략이 positive 검출을 망가뜨리지
  않았다는 **직접 증거가 없다.** 초기 문서는 모델 행동 리스크만 보았으나
  코드 결함도 발견했다. 후속 실제 API 비교에서는 역사 정탐 17→25/36,
  오탐 8→12/73, 새 미검출 1건으로 품질 기준을 충족하지 못했다.
- **09-26 20:08의 seen 불일치 1건이 재현되지 않았다.** 원인 불명.
  무해한 오보고인지 실제 누락인지 가리지 못했다. 재시도 안전장치는 넣었다.

### 검수자에게 묻고 싶은 것

1. false 생략 방식이 미탐 위험을 실질적으로 높이는가? 더 안전한 대안이 있나?
2. `seen` sentinel보다 나은 절단·누락 감지 방법이 있나?
3. positive 검출 무결성을 **비용 없이** 검증할 방법이 있나?
