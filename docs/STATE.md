한국투자증권 개인고객그룹용 **리스크 뉴스 자동 탐지·메일 발송** 파이프라인.

- 수집: 네이버 뉴스 API, **14시간 창** (회차 간 공백 방지)
- 단일 파일 구조: `naver_news_monitor.py` (약 7,000줄)
- 최종 선별: 회차당 0~5건

### 파이프라인

```
수집 → 하드제외룰(코드) → ① 1차 LLM 필터(배치 100)
  → ② 등급 재검증(전건) → 결정적 중복제거(제목·요약 유사도 0.92 + entity)
  → ③ 2차 본문검증(병렬 3) → ④ 대응방안 생성(병렬 3) → ⑤ 요약 → 메일 발송
```

### 모델 구성 (2026-09-26 현재)

| 단계 | 모델 | 상수 |
|---|---|---|
| ① 1차 필터 | `claude-haiku-4-5` | `CLAUDE_FILTER_MODEL` |
| ② 등급 재검증 | `claude-sonnet-4-6` | `CLAUDE_MODEL` |
| ③ 2차 본문검증 | 본인한정 → Sonnet / **전사발송 → `claude-opus-4-6`** | `CLAUDE_VERIFY_HIGH_MODEL` |
| ④ 대응방안 | `claude-sonnet-4-6` | `CLAUDE_ACTION_MODEL` |
| ⑤ 요약 | `claude-sonnet-4-6` | `CLAUDE_MODEL` |

②는 `CLAUDE_FILTER_MODEL != CLAUDE_MODEL`일 때만 작동한다. 1차를 저가 모델로
내렸을 때 상위 모델 검증이 사라지지 않게 하는 게이트다.

## 5. 미결 — 브랜치 `perf/filter-omit-negatives`

**main에 병합하지 않았다.** 검수 대상이다.

### 변경 내용

1. 1차 필터에서 **relevant:false 기사를 배열에서 완전 생략.** 출력에 없는 id는
   파서가 이미 false로 처리하므로 파싱 로직 변경 없음.
2. 배열 마지막에 `{"id":0,"seen":N}` sentinel 요구. 생략하면 '응답 잘림'과
   '전부 false'가 구분되지 않기 때문. id 0은 기사 id(1-base)와 겹치지 않아 무해.
3. `seen` 불일치 시 해당 배치 1회 재실행 후 더 많이 건진 쪽 채택.
4. 배치별 `expected/reported/returned`를 `filter_seen_detail`에 기록.

### 실측 결과

| 회차 | 수집 | 선별 | 기사당 출력 | seen 불일치 |
|---|---:|---:|---:|---:|
| 09-26 20:08 | 198 | 0 | **0.69 tok** | **1** |
| 09-26 20:13 | 197 | 0 | **0.32 tok** | 0 |

평균 12.97 → 0.69 tok/건 (**−94.7%**). **월 절감 약 $3.8.**

### 병합을 보류한 이유

- **`selected 0`이 4회 연속.** false 생략이 positive 검출을 망가뜨리지
  않았다는 **직접 증거가 없다.** (parser의 positive 경로는 미변경이므로
  코드 리스크는 아니고, 모델 행동 리스크다)
- **09-26 20:08의 seen 불일치 1건이 재현되지 않았다.** 원인 불명.
  무해한 오보고인지 실제 누락인지 가리지 못했다. 재시도 안전장치는 넣었다.

### 검수자에게 묻고 싶은 것

1. false 생략 방식이 미탐 위험을 실질적으로 높이는가? 더 안전한 대안이 있나?
2. `seen` sentinel보다 나은 절단·누락 감지 방법이 있나?
3. positive 검출 무결성을 **비용 없이** 검증할 방법이 있나?
